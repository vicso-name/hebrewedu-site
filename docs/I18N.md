# Internationalization (en / fr)

Single source of truth for how this site is bilingual. Read this before adding
or changing any page, in either language.

Related: `docs/LAYOUT.md` (layout guardrails), `docs/LESSON_PIPELINE.md` (how a
letter lesson is built), `docs/hebrew-alphabet-editorial-rules.fr.md` (FR
editorial rules), `docs/seo/README.md` (semantic core),
`docs/I18N_AUDIT.md` (the original read-only survey that planned this work).

Run `npm run check:i18n` before reporting any bilingual or SEO task done.

---

## 1. URL scheme

English is the default locale and is **unprefixed**. French lives under `/fr/`
with localized path segments. EN URLs never change and there are no redirects.

| English | French |
|---|---|
| `/` | `/fr/` |
| `/learn/hebrew-alphabet/` | `/fr/apprendre/alphabet-hebreu/` |
| `/learn/hebrew-alphabet/<slug>/` | `/fr/apprendre/alphabet-hebreu/<slug>/` |
| `/learn/hebrew-phrases/` | `/fr/apprendre/phrases-hebreu/` |
| `/terms/` | `/fr/conditions/` |
| `/website-privacy/` | `/fr/confidentialite/` |
| `/privacy/` | *(none — app policy, EN only)* |
| `/blog/` | `/fr/blog/` |
| `/blog/<slug-en>/` | `/fr/blog/<slug-français>/` |
| `/play/**` | *(none — English-only destination)* |
| `404.html` | *(none — see below)* |

**The 404 page is English-only, deliberately.** GitHub Pages serves one
`dist/404.html` for every unknown path on the site, `/fr/` ones included, and
does not honour a per-directory `/fr/404.html`, so there is nothing a French
counterpart could be wired to. `src/pages/404.astro` therefore reads `en` from
the dictionary like any other EN page; a French visitor reaches the French site
in one click through the nav's EN/FR switcher, which falls back to `/fr/` when
a page has no counterpart (`LangSwitch.astro`). It is `noindex, follow` and is
skipped by the `check:i18n` page inventory (§7).

Letter **slugs stay Latin-transliterated and identical across locales**
(`aleph`, `bet`, `gimel`, …). Only the *display* name differs: French uses the
SEO spellings in `src/i18n/fr-letters.ts` (Aleph, Beth, Guimel, Dalet, Hé …).
A shared slug is what lets hreflang pair the two pages mechanically.

**Blog slugs are the exception: they are not shared.** An FR post's slug is
French and SEO-chosen (`/fr/blog/voyelles-hebreu/` is the counterpart of
`/blog/how-to-read-hebrew-nikud/`), so there is no shared slug to pair on. The
two posts carry the same `translationKey` in their frontmatter instead
(`src/content.config.ts`; by convention it is the EN post's id), and that is
what the routes use to emit reciprocal hreflang. `/fr/blog/` keeps the English
word "blog", which is ordinary French — an owner decision, and final.

`/fr/blog/` and `/fr/blog/<slug>/` are **not built while
`src/content/blog/fr/` is empty** — both routes use a rest/dynamic parameter
and return no path, so there is no thin FR listing to index and no half-paired
hreflang. `astro build` logs a `collection "blogFr" … is empty` warning until
the first post lands; that is the expected state. See
`src/content/blog/fr/README.txt` for what the first post has to bring with it.

There is deliberately **no `astro:i18n` routing config**. The routes use custom
`getStaticPaths` plus a manifest-driven publication gate
(`src/lib/alphabet-course.mjs`) that the i18n router doesn't know about, so FR
is a parallel `src/pages/fr/**` tree instead. See `docs/I18N_AUDIT.md` §1 for
the full rationale.

## 2. How a page is made bilingual

**Shared template + dictionary.** One template renders both locales; each
locale has a thin page wrapper that supplies its own data and a `locale` prop.
No business logic is duplicated.

| Shared template | EN route | FR route |
|---|---|---|
| `components/home/HomePage.astro` | `pages/index.astro` | `pages/fr/index.astro` |
| `components/hub/AlphabetHubPage.astro` | `pages/learn/hebrew-alphabet/[...hub].astro` | `pages/fr/apprendre/alphabet-hebreu/index.astro` |
| `components/lessons/AlphabetLessonPage.astro` | `pages/learn/hebrew-alphabet/[lesson].astro` | `pages/fr/apprendre/alphabet-hebreu/[lesson].astro` |
| `components/phrases/PhrasesPage.astro` | `pages/learn/hebrew-phrases/[...landing].astro` | `pages/fr/apprendre/phrases-hebreu/[...landing].astro` |
| `components/legal/LegalPage.astro` | `pages/terms.astro`, `pages/website-privacy.astro` | `pages/fr/conditions/`, `pages/fr/confidentialite/` |
| `components/blog/BlogIndexPage.astro` | `pages/blog/index.astro` | `pages/fr/blog/[...index].astro` |
| `components/blog/BlogPostPage.astro` | `pages/blog/[slug].astro` | `pages/fr/blog/[slug].astro` |

These templates are registered as `LAYOUT_WRAPPERS` in
`scripts/check-layout.mjs`; a page rendering through one satisfies the
"every page uses Layout.astro" rule.

### The dictionary

```
src/i18n/
  index.ts       Locale type, the Dictionary interface, getDictionary(locale)
  en.ts          English values
  fr.ts          French values
  fr-letters.ts  FR display names for the 22 letters (display only, not slugs)
```

`Dictionary` is an **explicit interface**, not `typeof en`, so a missing or
extra key in either file is a type error. `tests/i18n-dictionary.test.mjs`
additionally asserts that `en` and `fr` have identical key sets at every level
and matching leaf value types.

Rules:

- **UI chrome only.** Lesson bodies and letter names are content, owned by the
  lesson pipeline — never add them here.
- Every component that renders text takes `locale?: Locale` (default `'en'`)
  and reads `getDictionary(locale)`. Never inline a user-visible English
  literal in a shared component.
- **Accessible labels count as chrome.** `aria-label`, `alt` and `title` are
  read aloud in the page's declared language, so they live in the dictionary
  too (`common.aria.*`).
- **Some "content" is really chrome.** `normalize.mjs` synthesizes a
  TRUE_FALSE exercise's option labels as the canonical English
  `True`/`False` (and `schema.mjs` enforces that), while grading keys off the
  option *id*. The visible wording therefore comes from
  `lesson.practice.booleanLabels` via `Practice.astro`'s `optionLabel()`, not
  from the normalized lesson.
- A **client-side** module can't import a dictionary per locale. Hand its
  strings over from the page instead:
  - `src/lib/lessons/practice-client.ts` reads the `#lesson-practice-strings`
    JSON payload emitted by `Practice.astro` (alongside `#lesson-grading`).
  - `src/lib/phrases/practice-client.ts` reads `data-phrase-*` attributes.
  Both keep English defaults in the module so it stays standalone-testable.
  `*Template` dictionary entries use `{placeholder}` tokens filled by
  `fillTemplate()`.
- `Layout.astro` owns `<html lang>`, `og:locale` and the `alternates` →
  `<link rel="alternate" hreflang>` tags. Pass it `locale` and `alternates`;
  never hand-write those tags in a page.

## 3. Parity rules

1. **A FR page links to FR pages.** If a French counterpart exists, link to it.
   Linking to the English page instead leaks readers and link equity — this was
   a real bug on the FR home (its phrases card pointed at `/learn/hebrew-phrases/`).
   Locale-gated helpers belong in the component: see `LearningResources.astro`,
   which picks `phrasesPathFr`/`phrasesPublishedFr()` on `fr`.
2. **An intentional FR → EN link must say so**, in French: either
   `(en anglais)` in the label (`t.common.gamesEnLabel`, `t.common.enOnlySuffix`),
   or `version anglaise` where the FR legal pages name the governing English
   text. The EN/FR language switcher is exempt — that *is* its purpose.
3. **hreflang is reciprocal or absent.** A page that declares alternates must
   declare `en`, `fr` *and* `x-default` (= the `en` URL), as absolute URLs, and
   its counterpart must point back. A page with no counterpart declares none.
4. **FR never publishes ahead of EN.** `validatePublicationManifest` in
   `src/lib/alphabet-course.mjs` enforces it; the FR lesson wrapper only emits
   hreflang/lang-switch once `lessonEnabled(slug, …, 'en')` is true.
5. **Per-locale publication state.** `src/data/alphabet-course.json` carries
   optional `locales.fr.{published,publishedAt,backfill}` per lesson. A lesson
   with no `locales` key behaves exactly as EN-only. Weekly publishing limits
   are counted **per locale** — FR editorial review is separate work.
6. **Sitemap holds every published page in both locales**, one mixed-locale
   sitemap. No FR page is `noindex` once published.

## 4. FR editorial rules

French copy follows `docs/hebrew-alphabet-editorial-rules.fr.md`. The two
rules this repo checks mechanically:

- **Address the reader as `tu`** everywhere except the legal pages
  (`/fr/conditions/`, `/fr/confidentialite/`), which use `vous`. Phrase
  *translations* may use `vous` when the Hebrew phrase addresses a shopkeeper
  or a stranger — that's the phrase's own register, not site voice.
- **French high punctuation takes a no-break space** (` `): before
  `:` `;` `?` `!` `»` and after `«`. In hand-authored copy (the dictionaries,
  page files, FR lesson editorial data) write the real character in the
  source string.

  For the French text this repo **cannot edit at rest**, the correction
  happens on the way to the page, via `src/lib/fr-typography.mjs`:

  | Source | Why it is read-only | Filtered in |
  |---|---|---|
  | `src/content/lessons/fr/**` — prompts, options, MATCH_PAIRS pair labels, explanations, study-block text | generated by `normalize-lesson.mjs` and verified against a pinned raw SHA | `Practice.astro`, `StudyBlock.astro` (both take `locale`) |
  | `src/data/hebrew-phrases.ts` — phrase headings, meanings, usage, gender notes, FAQ, exercises, dialogues | pinned by `phraseReviewFr`'s editorial sign-off SHA | `PhrasesPage.astro`, which deep-maps the FR data before passing it on |

  `localizeTypography(locale, value)` is the entry point: it deep-maps
  strings and is a **no-op on `en`**, so English output never changes. It is
  idempotent and safe on ids, hrefs, Hebrew and transliterations, none of
  which has a space before French high punctuation. It uses lookaround rather
  than captures so adjacent runs both match (`« de rien » ;` needs the fix
  twice).

  `check:i18n`'s `fr-typography` rule reads the rendered page, so it covers
  both paths. Its allowlist is empty and should stay that way — fix the
  source or the filter.
## 5. SEO rules per locale

- `<title>` ≤ 60 chars, meta description ≤ 155, exactly one `<h1>`, titles
  unique across the whole site.
- **No brand suffix in `<title>`**, in either locale (CLAUDE.md). The site name
  is carried by `og:site_name` and the `WebSite` schema.
- `og:locale` is `en_US` / `fr_FR`. Canonical is absolute, self, trailing slash.
- **JSON-LD speaks the page's language**: French `name`/`description`/breadcrumb
  text, `inLanguage: "fr"`, and every `hebrewedu.com` URL inside it points at an
  FR page. `inLanguage: "he"` is legitimate for embedded Hebrew.
- **Store links**: Google Play takes `&hl=fr` on FR pages
  (`src/data/site.ts`'s `storeHref(store, locale)`). App Store URLs stay
  country-neutral — Apple localizes by account region, so never add `/us/` or
  `/fr/` to an `apps.apple.com` URL.
- **Analytics**: `page_locale` is set once, in `loadGtag()`
  (`src/lib/analytics-consent.ts`), from `document.documentElement.lang`. It is
  never threaded through individual `track()` calls. See `docs/ANALYTICS.md`.
- **Semantic core**: every published FR page needs a `locale=fr` row in
  `docs/seo/core/pages.csv` whose `title`, `h1` and `meta_description` match
  what the page actually renders, plus a `primary_keyword` the title covers.
  Edit the CSV by hand, then run `npm run seo:build`. `check:i18n` fails on
  drift between the CSV and the built page.

## 6. Adding a page or a letter in both languages

### A letter lesson

Use the `add-letter-lesson` skill — it does EN and FR together by default
(`… fr` restricts to French, `backfill fr` prepares FR for letters already
published in EN). Manually, per `docs/LESSON_PIPELINE.md`:

```bash
# FR raw snapshot comes from the same lesson id with ?lang=fr
node scripts/normalize-lesson.mjs <slug> --locale fr --dry-run   # inspect
node scripts/normalize-lesson.mjs <slug> --locale fr             # write
```

- Identity (`scripts/alphabet-course/owner-letter-map.v2.json`) is shared: same
  slug, order, glyph and `source_lesson_id` for both locales.
- Editorial data file: `src/data/lessons/fr/<slug>.json` — FR `title`,
  `description` and `copy`, re-authored in French, with holdouts and overrides
  derived from the **FR** snapshot's own `sourceIndex` values.
- Normalized output: `src/content/lessons/fr/<slug>.json`. **Never hand-edit
  it** — it is generated, and `title`/`description` are copied from the
  editorial data file. Change the data file and re-run normalize instead.
- Publish by setting `locales.fr.published` in `src/data/alphabet-course.json`.

### A blog post

The routing, templates, dictionary and checks are already in place (this is the
FR-blog infrastructure step); adding a post is content work plus bookkeeping.

1. Write `src/content/blog/fr/<slug-français>.md`. The slug is chosen for
   French search, not transliterated from the EN one.
2. Set `translationKey` to the **EN post's id** — that, not the slug, is what
   pairs the two for reciprocal hreflang. Both routes then emit en + fr +
   x-default on their own; neither needs editing.
3. Set `categoryKey` to one of `src/i18n`'s `blog.categories` keys, so the two
   locales stay on one taxonomy. Give `readingTime` a French value
   (`9 min de lecture`).
4. French copy uses `tu`; high punctuation takes a no-break space, in the
   **frontmatter** (`title`, `description`) as well as the body —
   `fr-typography` checks the body, `fr-typography-head` the metadata.
5. `<title>` ≤ 60 with no brand suffix, meta description ≤ 155, one `<h1>`
   (the template renders it from `title`, so body headings start at `##`).
6. Add a `locale=fr` row to `docs/seo/core/pages.csv`, then `npm run seo:build`.
   **The first FR post also needs a row for `/fr/blog/` itself**, which starts
   building at the same moment, and the FR Nav/Footer "Blog (en anglais)"
   labels should then point at `/fr/blog/` instead of `/blog/`.
7. `npm run build` and `node --test tests/`.

### Any other page

1. Add the FR route under `src/pages/fr/**` with a localized path segment, as a
   thin wrapper over the shared template (create the shared template first if
   the EN page doesn't have one yet — don't fork the page).
2. Add its strings to `src/i18n/fr.ts`, and the same keys to `en.ts`.
3. Pass `locale="fr"`, `alternates` (en + fr + x-default) and `langSwitch` to
   the template, and add the matching `alternates`/`langSwitch` to the **EN**
   page so hreflang is reciprocal.
4. Add it to the sitemap (`src/pages/sitemap.xml.ts`).
5. Add a `locale=fr` row to `docs/seo/core/pages.csv` (cluster + primary
   keyword, no cannibalization), then `npm run seo:build`.
6. `npm run build` (runs `check:layout` before and `check:i18n` after) and
   `node --test tests/`.

## 7. check:i18n

`scripts/check-i18n.mjs`, run by `npm run check:i18n`, by `postbuild` (so a
violation fails `npm run build`), and as its own CI step in
`.github/workflows/deploy.yml`.

It runs **after** the build rather than in `prebuild` like `check:layout`,
because every rule reads the rendered HTML in `dist/` — `<html lang>`,
canonical, hreflang reciprocity, JSON-LD, sitemap coverage. None of that exists
before `astro build`.

The **page inventory** (`SKIP_PREFIXES`/`SKIP_EXACT`, above the rules) is what
counts as a page at a URL in the first place, and is not a per-rule allowlist:
synced game bundles, the Search Console token, the three fullscreen game
canvases, and `/404` — the error document GitHub Pages serves for every unknown
path, which has no URL of its own, so canonical, hreflang and sitemap coverage
are all meaningless for it (`src/pages/404.astro`).

Rules: `html-lang`, `og-locale`, `canonical-missing`/`canonical-self`,
`hreflang-missing`/`-incomplete`/`-relative`/`-target-missing`/`-x-default`/
`-not-reciprocal`, `title-missing`/`-length`/`-brand-suffix`/`-duplicate`,
`description-missing`/`-length`, `h1-count`, `jsonld-invalid`/`-inlanguage`/
`-cross-locale-url`, `fr-unmarked-en-link`, `store-play-locale`,
`store-appstore-country`, `sitemap-missing`/`-noindex`/`-stale`,
`robots-fr-blocked`/`robots-sitemap`, `fr-english-ui`, `fr-english-aria`,
`fr-typography`, `fr-typography-head`, `seo-core-missing`/`-locale`/`-keyword`/
`-keyword-not-in-title`/`-title-drift`/`-meta-drift`/`-h1-drift`, `anchor-missing`
(an in-page `href="#…"` — a blog post's jump-nav or an FAQ answer linking back
into its own article — with no matching `id` on that page; checked on every
locale, not just FR), `fr-alphabet-anchor-not-hub` (an FR anchor whose visible
text contains "alphabet hébreu" must link to the hub,
`/fr/apprendre/alphabet-hebreu/`, or one of its own pages (a letter lesson) —
the hub owns that keyword exclusively per
`docs/seo/research/fr/BLOG_FR_PLAN.md`'s "Keyword ownership" note, but a
lesson page is part of the hub's own course, not a competing page; reword the
anchor or retarget the link outside that tree; exempt when the anchor is
simply the destination page's own title, e.g. a blog-post card linking to
itself).

A separate, non-build-failing warning (printed, not a `findings` rule) flags
a single-word italic on an FR page spelled with "ch" — usually a Hebrew
transliteration that kept the EN "ch" digraph for the guttural Khet/Kaf sound
instead of the French "kh" (`docs/hebrew-alphabet-editorial-rules.fr.md`).
It's scoped to single lowercase-ish tokens so it doesn't fire on ordinary
italicized emphasis or an intentional all-caps sound description like `*CH*`
— still a heuristic, read the output rather than trusting it blindly.

Policy, same as `check:layout`: fix the code, or add an ALLOWLIST entry with a
one-line reason. **Never widen an allowlist to silence a finding** — if you
believe an exception is needed, ask the owner first.

## 8. Known gaps

Open items this guardrail allowlists rather than hides. Each entry names the
allowlist it lives in.

| Gap | Where | Why it isn't a lint fix |
|---|---|---|
| `/blog/hebrew-alphabet-complete-guide/` keeps `… | HebrewEdu Blog`, which is also why its title is 72 chars | `BRAND_SUFFIX_ALLOWLIST`, `TITLE_LENGTH_ALLOWLIST` | Owner decision: this one post holds the suffix until end of October 2026. Its own title is 55 chars, so removing the suffix closes both rows at once. |
| 5 blog meta descriptions 156–159 chars | `DESCRIPTION_LENGTH_ALLOWLIST` | Trimming a ranking post's description is an SEO edit needing owner sign-off, not a lint fix. |
| `/play/`, `/play/alef-bet-rush/` titles still carry the brand suffix | `BRAND_SUFFIX_ALLOWLIST` | A games SEO pass the owner has to sign off on. |

Closed since the first audit: FR lesson-body and FR phrases typography (now
corrected at render time, §4); the `og:title` brand suffix (removed from both
home pages, with `og-title-brand-suffix` now guarding it); and the `gimel`
keyword/title mismatch (French volume + SERP research picked **Guimel**, so the
page and its primary keyword now agree). `dalet` has since been renamed
Daleth -> **Dalet** across its title, meta, H1, breadcrumb and body copy to
match the same research — see `docs/seo/research/fr/LETTER_SPELLINGS_FR.md`.

Closed by the FR-blog infrastructure step: the blog-wide
`… | HebrewEdu Blog` convention (dropped from the shared template, the
hand-written `seoTitle`s and the listing, which took 10 of the 11 over-length
titles under 60 with it); the 6 `<h1>`s on
`/blog/meet-the-new-verb-directory/` (its body headings now start at `##`, so
the `h1-count` rule needs no exemption at all); and FR **head** typography —
the new `fr-typography-head` rule found a plain space before `:` in the FR
Aleph lesson's and the FR phrases page's meta descriptions, now fixed at the
source and at render time respectively.

The prefix-wide `LENGTH_EXEMPT_PREFIXES` is gone: what remains is three
explicit per-URL rows above. `TYPOGRAPHY_ALLOWLIST` and
`KEYWORD_TITLE_ALLOWLIST` are both still empty.
